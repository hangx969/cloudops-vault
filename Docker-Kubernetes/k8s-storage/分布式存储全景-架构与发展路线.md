# 分布式存储全景：架构、发展路线与选型

Ceph、MinIO、JuiceFS 和 Alluxio 经常一起出现在存储选型讨论中，但它们诞生于不同年代，解决的问题也不同。理解项目的来历、接口和架构取舍，才能判断它是否适合当前负载。

开源分布式存储的发展可以沿着几条路线看：1999 年开始的 Lustre 研究、2003 年的 GFS 论文、2006 年出现的 HDFS 和 Ceph，以及 2025 年 DeepSeek 开源的 3FS。互联网数据增长、容器化和 AI 负载先后推动了架构变化。本文先解释共同问题，再梳理存储形态、发展路线和阅读路径。

## 分布式存储要解决什么问题

单台服务器的存储有三个限制：

- 容量：单块磁盘容量和服务器盘位都有上限。
- 性能：网卡、控制器和总线按单机配置，吞吐受这些部件约束。
- 可靠性：没有其他副本时，机器损坏可能导致数据丢失；部件越多，需要处理的故障也越多。

![单机存储的容量、性能与可靠性限制](https://raw.githubusercontent.com/hangx969/upload-images-md/main/2026/10/11/storage/storage-overview-01-single-node-limits.svg)

把数据分散到多台机器后，限制转化为四个需要共同设计的问题：

| 问题 | 需要决定什么 | 常见方案 |
| --- | --- | --- |
| 数据放在哪里 | 写入目标、读取位置和节点变化后的迁移 | 哈希、范围划分、一致性哈希、CRUSH |
| 数据如何避免丢失 | 冗余方式与可容忍的故障范围 | 多副本、纠删码 |
| 多份数据如何保持一致 | 客户端能看到什么版本、何时确认写入 | 强一致、弱一致、最终一致 |
| 节点故障后如何恢复 | 故障检测、数据重建和服务切换 | 心跳、恢复、再平衡 |

![数据放置、冗余、一致性与故障恢复](https://raw.githubusercontent.com/hangx969/upload-images-md/main/2026/10/11/storage/storage-overview-02-distributed-storage-challenges.svg)

不同项目的主要差异，就在这些问题的答案中。例如，Ceph 用 CRUSH 处理放置，MinIO 使用纠删码提供冗余，Swift 采用最终一致性的设计，HDFS 则集中管理文件系统元数据。读架构图时，可以先沿着这四个问题追踪数据和控制信息。

## 文件、对象和块存储

三种形态的区别在对外接口和语义，底层的数据分布与冗余机制可以相同。

文件存储提供目录树和文件操作，通常通过 POSIX 风格的接口挂载，支持打开、追加、随机读写和多客户端共享。训练数据集、媒体制作、共享代码仓库都属于典型场景。

对象存储通常使用“桶 + 键”寻址，通过 HTTP API 上传和读取对象。常见 S3 接口以对象为操作单位，不提供普通文件系统那样的任意字节就地修改。它适合图片、视频、备份和日志等海量非结构化数据，尤其是写入后较少修改的数据。S3 已成为常用的兼容接口。

块存储提供裸块设备。操作系统可以在其上创建 XFS、ext4 等文件系统，再像本地磁盘一样使用；也可以直接把裸块设备交给应用。数据库卷和虚拟机系统盘常用这种接口。

![文件、对象和块存储的接口与场景](https://raw.githubusercontent.com/hangx969/upload-images-md/main/2026/10/11/storage/storage-overview-03-file-object-block.svg)

| 维度 | 文件 | 对象 | 块 |
| --- | --- | --- | --- |
| 寻址方式 | 路径 | 桶 + 键 | 逻辑块地址 |
| 修改方式 | 随机写、追加 | 常见接口为整体覆盖 | 任意块写入 |
| 共享访问 | 多客户端同时挂载 | 天然多客户端 | 常见用法为单节点挂载 |
| 原文给出的典型容量量级 | TB～PB | PB～EB | 每卷 GB～TB |

容量量级用于对照常见场景，不是接口本身的硬限制。块设备的多节点写入还取决于存储驱动、锁机制和上层文件系统，不能仅靠“能挂载”判断数据是否安全。

Ceph 在同一套 RADOS 底座上提供 RBD、RGW 和 CephFS；JuiceFS 则把对象存储作为数据底座，对外提供文件接口。因此，选型既要看应用需要什么接口，也要看接口下面的数据路径。

## 四条发展路线

开源分布式存储并非从同一个架构演进而来。按最初的负载和设计目标，可以分成四条路线。

![HPC、大数据、统一扩展和云原生四条路线](https://raw.githubusercontent.com/hangx969/upload-images-md/main/2026/10/11/storage/storage-overview-04-four-lineages.svg)

### HPC：并行文件系统

超算的数千乃至更多节点需要同时读写同一批数据，普通文件系统难以承载这种并发。并行文件系统把元数据与数据分开，客户端直接访问数据节点，以聚合带宽服务大规模计算。

这条路线从 Lustre、BeeGFS 延伸到面向 NVMe 和 RDMA 的 DAOS，再到 DeepSeek 3FS。3FS 属于 AI 负载推动的新一代设计，相关细节见 [[Docker-Kubernetes/k8s-storage/开源存储DeepSeek 3FS，AI原生的并行文件系统|DeepSeek 3FS]]。

### 大数据：海量数据的批处理存储

2003 年 Google 发表 GFS 论文，公开了架构思路，没有开放对应代码。开源社区随后构建了 Hadoop 的 HDFS，生态中又出现 Ozone 和 Alluxio。

这些项目围绕网页、日志等海量数据展开，但分工不同：HDFS 承担分布式文件存储，Ozone 提供对象存储，Alluxio 位于计算与底层存储之间，负责统一访问和数据加速。

### 统一扩展：用通用服务器构建存储服务

这条路线希望用通用服务器实现存储阵列或扩展型 NAS 的能力。GlusterFS 面向扩展型 NAS，Ceph 同时提供块、文件和对象接口，MooseFS 走轻量 POSIX 文件系统路线。

JuiceFS、CubeFS 等新一代项目也可以沿这条路线理解。它们对元数据、数据存储和扩展方式做了不同取舍。参见 [[Docker-Kubernetes/k8s-storage/开源存储Ceph|Ceph]] 和 [[Docker-Kubernetes/k8s-storage/开源存储CubeFS，分布式存储|CubeFS]]。

### 云原生：让存储参与 Kubernetes 编排

应用进入 Kubernetes 后，存储需要通过声明式对象申请、挂载和回收，并配合 Pod 调度。CSI、存储 Operator 和卷生命周期管理由此成为关键接口。

Rook 负责在 Kubernetes 上编排 Ceph，Longhorn 和 OpenEBS 提供面向容器的存储能力，Fluid 则组织数据集和加速运行时。它们处于不同层次，不能只看是否支持 PVC 就当作同类产品。Longhorn 的具体设计见 [[Docker-Kubernetes/k8s-storage/开源存储Longhorn，K8s的轻量块存储|Longhorn]]。

四条路线长期共存。一个数据中心可以同时运行 HPC 并行文件系统、HDFS、对象存储和 Kubernetes 块存储，各自服务不同负载。AI 需求也会影响这些路线，而不只属于某一条。

## 关键时间节点

![1999—2025 年的分布式存储时间线](https://raw.githubusercontent.com/hangx969/upload-images-md/main/2026/10/11/storage/storage-overview-05-storage-timeline.svg)

原文选取的主要节点如下：

| 年份 | 节点 | 在发展路线中的作用 |
| --- | --- | --- |
| 1999 | Lustre 研究起步 | HPC 并行文件系统；后来持续用于超算 |
| 2003 | GFS 论文 | 影响后续的大数据存储设计 |
| 2006 | HDFS、Ceph | 分别面向大数据文件存储和统一分布式存储 |
| 2010 | OpenStack Swift | 云平台中的对象存储 |
| 2013 | Alluxio 前身 Tachyon 开源 | 计算与存储之间的数据共享和编排 |
| 2015 | MinIO | 在通用服务器上提供 S3 兼容接口 |
| 2016 | Rook | 在 Kubernetes 中部署和管理存储 |
| 2018 | CubeFS | 电商场景中的大规模存储实践 |
| 2021 | JuiceFS 开源 | 元数据与对象存储数据分离 |
| 2025 | DeepSeek 3FS | 面向 AI 集群的并行文件系统 |

图外还有几个节点：GlusterFS 于 2005 年起步，MooseFS 于 2008 年开源，Longhorn 和 OpenEBS 于 2017 年起步，CubeFS 于 2019 年进入 CNCF。JuiceFS 的公司创立时间与 2021 年开源时间也应分别理解，原文给出的创立时间是 2017 年。

> [!note] Alluxio 时间线
> 原文把 Alluxio 更名写在 2014 年。创始人资料记载：项目研究始于 2012 年，2013 年 4 月开源；Tachyon 更名为 Alluxio、发布 1.0 是 2016 年的节点。参见 [Alluxio 创始人说明](https://www.alluxio.io/blog/alluxio-formerly-tachyon-is-entering-a-new-era-with-10-release)。

## 三次主要的负载变化

![大数据、云原生和 AI 负载推动的三次变化](https://raw.githubusercontent.com/hangx969/upload-images-md/main/2026/10/11/storage/storage-overview-06-three-waves.svg)

### 大数据浪潮：约 2006—2012 年

搜索引擎、网页和日志系统需要把数据分散到数百台通用机器上。HDFS、Ceph 和 GlusterFS 等项目体现了横向扩展的思路：单机不够就增加节点，用副本或纠删码提高数据耐久性。

### 云原生浪潮：约 2014—2020 年

容器化推动存储参与编排，CSI、Operator 和声明式卷管理逐渐形成通用接口。同一时期，S3 兼容接口普及，MinIO、SeaweedFS 等对象存储项目发展起来。

原文还从选型角度提示商业模式的变化：Red Hat 收购 Inktank，以及 MinIO 许可证调整，都影响了支持服务、治理和长期维护。技术接口之外，这些也是选型需要评估的因素。

### AI 浪潮：约 2023 年至今

训练和推理出现了不同于传统业务的 IO 模式：

- checkpoint：集中写入大量训练状态，需要较大的持续写带宽。
- 训练数据集：海量小文件和高并发随机读取，既考验数据吞吐，也考验元数据路径。
- 推理 KV Cache：在显存和更便宜的存储层之间迁移，需要分层和快速读取。

JuiceFS、Alluxio、CubeFS 等已有项目进入 AI 场景，3FS 等新项目则直接围绕这些负载设计。这一阶段仍在演进，不能把某一种架构当作所有 AI 负载的通用答案。

## 讨论范围

原系列按“开源、以存储为主要职责、在某个阶段具有代表性”选择项目，边界如下：

- 分布式数据库和 KV 系统另属一个领域。HBase、Cassandra、etcd、TiKV 虽然也分布式存储数据，但接口到键值或 SQL，原目录的第 28 篇讨论这条边界。
- GPFS / Spectrum Scale、WEKA、VAST、Panasas 等闭源商业产品只用于对比，不设独立项目篇。
- ext4、ZFS、XFS 等单机文件系统不属于讨论主体。
- Kafka 等消息队列、Iceberg 等数据湖表格式与存储有关，但主轴不同。
- IPFS / Filecoin、Arweave 的设计与主流集群存储不同，作为去中心化存储的延伸阅读。
- 纯研究性质、代码已经停止活动的实验项目不进入主要项目列表；失败或退场项目可作为专门的教训篇讨论。
