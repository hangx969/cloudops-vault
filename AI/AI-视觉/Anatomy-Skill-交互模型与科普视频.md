# Anatomy Skill：交互模型与科普讲解视频

> 来源：[《分享一个最近很惊艳的开源 Skill，一句话让 AI 搓出任何原理的科普视频》](https://mp.weixin.qq.com/s/VuJsVTvyNIK8GRTL95n-Qw?scene=1&click_id=1652332932)，卡兹克、tashi，2026-10-15。
> 项目：[wheresryan22/anatomy](https://github.com/wheresryan22/anatomy)。

Anatomy 是一个把原理做成交互模型的开源 Skill。它让 Agent 展示物体的零件、结构和运动过程，帮助读者观察一个系统如何工作。原文在这些动画的基础上，进一步让 Agent 制作带讲解、配音和音效的科普视频，尝试解决初学者“看得到运动，却不明白为什么”的问题。

## 工作方式：用物体的运转解释原理

Anatomy 的设计理念是：

> The object is the explanation.
> 物体本身，就是解释。

它尝试把抽象知识转化成一套可观察、可操作的装置模型，让读者通过零件之间的关系和运动过程理解原理。原文主要展示两类例子：

- 机械表：可以手动转动发条，观察内部零件如何运转，也可以拆开各部分查看结构。
- 劳斯莱斯 Trent 970 发动机：通过带 1/4 剖面的模型，展示风扇、压气机、燃烧室和涡轮等内部结构。

对于已有相关知识的人，这类细致的动画有助于观察结构。但对初学者来说，仅看零件运动，甚至配合 Skill 自带的文字说明，仍可能无法理解每个零件是什么、有什么作用，以及整个系统为什么能工作。

因此，原文把两种使用方式放在一起尝试：先用交互模型探索结构，再用配有旁白的视频逐步解释过程。

## 安装与机械表交互演示

### 安装 Skill

原文给出的方法是让 Agent 查找并安装 Anatomy，或者直接发送下面这段请求：

```text
帮我安装一下这个skill：https://github.com/wheresryan22/anatomy/tree/main
```

这段文字是发给 Agent 的安装请求。

### 生成交互模型

原文引用了下面这条机械表演示提示词：

```text
/anatomy explain how a mechanical watch keeps time, interactive
```

它要求生成一个交互演示，解释机械表如何计时。读者可以操作发条、观察零件运动，并拆开模型查看各部分结构。

## 从交互动画到带配音的讲解视频

初学者需要的解释通常包括：眼前是什么零件、现在发生了什么、为什么发生，以及它在整个系统中起什么作用。原文据此让 Agent 在 Anatomy 动画基础上生成有讲解、有配音的科普视频。

按原文记录，这一过程包含以下要求和调整：

1. 指定要学习的主题，要求制作带讲解和配音的视频。机械表案例使用原文所称的 Opus 5.5，推理强度为高。
2. 根据需要明确讲解深度。原文的显卡视频较简略，TCP 三次握手视频则要求更详细的解释。
3. 检查配音效果。机械表视频第一次默认使用 macOS 自带的语音合成，作者认为声音不自然。
4. 继续要求 Agent 更换配音。作者要求改用火山的配音后，一次完成了调整。

Anatomy 在原文中主要输出交互式 HTML 页面；配音和视频是作者继续要求 Agent 制作的交付物。项目说明也将核心产物定义为交互图形，可交付为 HTML、SVG 或组件。因此，生成交互模型与完成配音视频应分别理解。[Anatomy 项目说明](https://github.com/wheresryan22/anatomy#what-it-makes)

## 原文案例与讲解组织

### 机械表：解释零件之间的关系

原文的机械表视频依次说明了有哪些零件、各自的作用、彼此的关系，以及计时原理。作者观察到，动画中的齿轮转动能够相互啮合，并配有对应音效。

第一版视频时长为 2 分 22 秒，更换配音后的版本为 2 分 21 秒。作者认为，这种形式比单纯展示动画更适合自己这样的初学者：看完后能对机械表的工作方式形成初步认识，也更容易知道下一步可以继续学什么。

### 显卡：按一次画面生成过程组织内容

作者用同样的方法生成了一段 1 分 45 秒的显卡原理视频，记录为一次生成、没有修改。讲解顺序是：

1. 显卡用来做什么。
2. 包含哪些组件。
3. 这些组件如何组装。
4. 一帧画面如何计算出来。
5. 显卡为什么计算得快。
6. 画面如何连续动起来。
7. 显卡如何散热。
8. 显卡的输入和输出分别是什么。

讲解到某个部分时，画面会展示或高亮相应组件。原文认为这种组织方式较清晰；如果希望讲得更细，可以在提示词中继续明确要求。

作者还用原文所称的 Sonnet 5.5、推理强度高，生成了一段 2 分 8 秒的显卡原理视频。他认为，用于自己学习时，这个版本的效果已经够用。

### TCP 三次握手与刹车结构

| 主题 | 原文记录的设置 | 视频时长 | 体验与限制 |
| --- | --- | --- | --- |
| TCP 三次握手 | Opus 5.5，Ultra 推理强度，要求详细讲解 | 5 分 16 秒 | 作者认为讲解清楚，但部分英文发音有问题；一位通信专业背景的同事也给出了正面反馈 |
| 刹车构造 | 原文未单独说明模型设置 | 4 分 26 秒 | 展示了将这一方法用于刹车结构科普的例子 |

这些是原文作者的体验与他人反馈，不能据此认定视频中的技术细节全部正确。

## 模型、额度与生成耗时

以下模型名称、推理档位、额度和耗时均按作者当时的记录保留，属于案例经验。

- 约 5 分钟的 TCP 三次握手视频，消耗约为作者 200 美元 Claude Max 会员周额度的 1%。
- 作者制作的其他约 5 分钟视频，消耗也大致在周额度的 1% 左右。
- 使用 Opus 5.5、Ultra 推理强度生成约 5 分钟的视频，耗时约 1.5 小时。
- 作者认为，对外发布并追求精细零件时，可以尝试更强的模型和更高推理强度；只用于自己学习时，可以先生成简单版本，尝试较省额度的配置。

额度消耗和等待时间是两个不同的考虑因素。原文中的额度占比较低，但生成过程仍需较长时间。

作者转述了 Anatomy 开发者对耗时的解释：“细节需要时间，所以我宁愿展示真实数字，而不是猜测。”[项目说明的限制部分](https://github.com/wheresryan22/anatomy#limits)也明确表示，零件规划、几何构建、检查和局部审阅会让制作过程较慢。

原文还记录了一个 Transformer 演示的例子：Agent 尝试训练一个小模型，随后该会话被 Claude 限制；作者将其描述为敏感行为判定。这是一次会话中的经历，具体触发机制未得到独立核实。

## 学习材料的四种形式

原文把 Anatomy 的实践与 Karpathy 关于理解大模型输出的讨论联系起来，并转述了他最看好定制讲解视频的判断。相关背景见 [[AI/行业动态/Karpathy-大模型输出理解技巧-文字图解网页视频|Karpathy：让大模型输出更容易理解的四种技巧]]。

### 文字：借用清晰写作的约束

原文介绍了 ASD-STE100 简化技术英语规范。它最初面向航空维修文档，对用词和句式作出约束，例如限制句子长度、使用主动语态、同一含义尽量使用一致的词语，以减少歧义。

Karpathy 的建议是让 AI 参考这种规范解释问题。原文用榫卯作为例子，对比普通说明和参考规范后的表达。这里借用的是清晰写作原则；中文说明不因此成为符合 ASD-STE100 的技术英语文档。

### 图解、交互网页与讲解视频

| 形式 | 适合解决的问题 |
| --- | --- |
| 文字 | 快速查阅定义和说明 |
| 图解 | 展示组件关系、结构和联系 |
| 交互式 HTML 网页 | 让读者自己操作、拆解和探索 |
| 讲解视频 | 按顺序逐步理解一个过程，让画面与解释配合 |

原文还围绕同一个榫卯主题，展示了一次生成的 HTML 交互页面和 Anatomy 讲解视频；对应演示时长分别为 1 分 29 秒、2 分 18 秒，HTML 页面使用 Opus 5.5 生成。

这些形式各有用途。不同知识、读者背景和学习阶段，需要的解释方式可能不同。交互网页适合主动探索，视频则更适合跟随一条安排好的讲解顺序。

## 使用边界

AI 生成的动画即使画面精细，也不能保证每一处机械结构、计算过程和讲解内容都正确。用于专业知识学习时，具体参数和关键原理仍需核对。旁白还可能存在英文发音等问题，也需要检查。

过去寻找学习材料，通常是在别人预先制作的文章和课程中选择：有的太浅，有的太专业，冷门问题还可能找不到对应内容。原文提出的变化是，可以让 AI 根据当前的问题和需要临时制作一份材料，帮助读者继续探索一个具体主题。
